# Mutations

A test that has never failed has not shown it can. Each row is a deliberate
break in the **implementation** — never in a test's assertion — the test that
went red, and the message it gave. Every break was reverted after its run.

Every test in the repository has been made to fail by at least one row below:
the 106 in `packages/partner`, the 19 in `packages/cases` and the 110 in `packages/api`. A new test is not done until it has a row too.

## Tests that could not fail, found on the way

Running the mutations is what found these. Each one passed whatever the code
did.

- **"refuses a timestamp that is not plain seconds".** It sent `' 1614265330'`
  and friends with the vector's original signature. The timestamp is part of
  what is signed, so each one failed the signature whatever the format check
  did. It now signs every malformed timestamp properly, so only the format
  check can refuse it — row 9.
- **"treats a header that is not base64 as a wrong signature".** It sent
  `v1,not base64!`, which the verifier splits at the space into `v1,not` — and
  `not` is valid base64. Nothing ever threw. It now sends `v1,***` — row 6.
- **"answers an unknown variant … with a problem document".** It asked for
  `/members/x`, so the 404 came from the missing member whether the variant
  was checked or not. It now asks for a real member — row 14.
- **"a body that is not an object".** An array or a number failed the field
  checks whatever the object check did. The object check was removed as
  redundant, and the test now also sends `null`, the one body that would
  otherwise reach the destructuring — row 31.
- **"has a status for every version that is expected to fail something".** It
  checked the status was not `null`, but a blank cell parses to `''`, which is
  not `null` either. A version with no status passed it. It now requires one of
  the two statuses there are — row 128.
- **The version-by-version test's own failure message.** It compared three
  arrays inside an object, so a red read `expected { …(3) } to deeply equal {
unexpectedlyRed: [], …(2) }` — no case, no version. Not a test that could not
  fail, but one that failed without saying why. It now throws a sentence per
  problem: `security/tampered-body was failed, and the table does not expect
ignores-signature to fail it`.
- **"unvalidated-points still earns and redeems valid points exactly".** It
  earned 100, redeemed 30 and checked the balance once, at the end. With the
  version also one point short on each, the earn is 1 under and the redemption
  1 over, the two cancel, and the end balance is the right 1,070. It now checks
  after each step — row 147.
- **"tokens are URL-safe, long, and different every time".** It checked one
  token against `^[A-Za-z0-9_-]{43}$`. A 43-character base64 string has about
  a one-in-four chance of holding no `+` or `/` at all, so with the replacement
  removed it would still have passed one run in four. It now checks fifty —
  row 174.
- **"still refuses a replay inside the window afterwards".** Its first version
  used an id seen in the same second as the purge, and the mutation that made
  the purge forget every id (row 213) survived it: `seen_at < now` is false in
  the same second. It now backdates the id by a minute, so the id is inside the
  window and not hidden by the clock, and row 213 turns it red.
- **Not caught.** The boundary of the `session_starts` cleanup (`<=` against
  `<`) has no test: the cases sit a minute either side of the window, and
  testing the exact second would depend on the clock not ticking between the
  insert and the sweep. A wrong boundary there would keep or delete one row a
  second early or late, and the rate limit's own statement resets such a row to
  a count of one either way.
- **Not shown separately.** The 404 test and the serves-under-`/api` test both go
  red under row 223 and under nothing else I tried. A mutation meant to make
  only the 404 test fail (the routes also registered at the old paths) did not
  do that — `basePath('/')` on an app that already has a base path still sits
  under `/api` — so it was not counted and nothing was recorded for it.
- **Equivalent, not a survivor.** Setting the two headers before `await next()`
  instead of after it changes nothing a client sees: Hono keeps headers set
  early and puts them on the response when it is made. It was tried and the
  test stayed green, which is right, so it has no row.
